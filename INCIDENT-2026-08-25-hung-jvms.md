# Инцидент 2026-08-25: зависшие JVM (jdt.ls + bazel-сервер)

Диагностика зависших java-процессов на машине разработчика. Дополняет
[PERFORMANCE_PLAN.md](PERFORMANCE_PLAN.md) — не пересказывает его: структурные проблемы
(P0–P5, B1) там уже описаны, здесь зафиксировано **как дефект B1 реально сработал в поле**
и какие пробелы плана он вскрыл.

## TL;DR

Дефект **B1** (`BazelWorkspace` кидает `CoreException` на любом ненулевом exit code, а
`--keep_going` отдаёт exit 3 при частичном успехе) сработал не из-за сломанного `BUILD`,
а из-за **временной сетевой недоступности внешних репозиториев**. Так как неудача нигде
не кешируется и backoff отсутствует, jdt.ls повторял полный импорт монорепо
**каждые ~16 секунд с 00:44 до 07:00+** — порядка 1400 итераций. Всё это время
bazel-сервер не простаивал, поэтому `--max_idle_secs=10800` не срабатывал и он не выгружался.

Итог: ~2.3 ГБ java-процессов, один из которых (bazel-сервер `audienzz`) остался вообще
без клиента и висел бы ещё до 3 часов.

## Корневая причина

### Триггер: недоступные внешние репозитории

Запрос импортёра идёт по **всему** репозиторию — `kind('java_library|java_binary|java_test rule', //...)`
с `--output=xml --keep_going --noshow_progress`.

Шаблон `//...` загружает все пакеты, включая не-Java. Ночью не тянулись:

- `@@rules_oci++oci+node22_linux_amd64` — не получить image manifest
- `@@rules_oci++oci+node_playwright_linux_amd64` — то же
- `@@+helm_charts+clamav` — `GET returned <none>` с `https://registry.adnz.co/v2/audienzz/charts/clamav/manifests/…`
  (тянет `platform/infra/audienzz/clamav/BUILD.bazel` → `clamav_dev`, `clamav_prod`)

bazel печатает `ERROR: command succeeded, but there were loading phase errors`
и отдаёт **exit 3**.

### Усилитель: B1 + отсутствие negative caching

`BazelWorkspace.run()` бросает `CoreException` на любом ненулевом exit code — это
известный дефект **B1**. Но в поле он оказался хуже, чем «один сломанный BUILD валит импорт»:

1. Ошибка **не кешируется** — ни как negative-запись, ни как «не пытайся N минут».
2. **Backoff отсутствует** — jdt.ls перезапрашивает импорт, тот сразу снова падает.
3. Каждая итерация — **полная загрузка графа монорепо** в bazel-сервере, то есть сервер
   постоянно занят → `--max_idle_secs=10800` не срабатывает никогда.

Проверка после инцидента: тот же запрос вручную даёт **exit 0** и 442 java-таргета.
То есть сбой был чисто транзиентный, а расширение из-за него сутки жгло CPU.

### Почему процессы копятся

- jdt.ls осиротевает (PPID 1) при перезапуске extension host и выходит **только** на
  следующем опросе parent-watchdog — отсюда лаг между сиротством и `forcing server exit`.
- Порождённый им bazel-сервер **переживает клиента** и держит ~1.15 ГБ до idle-таймаута
  (3 часа при `--max_idle_secs=10800`).
- Умножается на число окон: три workspace (`audienzz`, `audienzz_copy`, `vscode-bazel-java`)
  = три jdt.ls c `-Xmx4G` и три отдельных output base
  (`audienzz`, `audienzz_copy`, `audienzz_old`), у каждого свой сервер + persistent workers.

> Важно при диагностике: bazel-сервер **всегда** имеет PPID 1 — он детачится by design.
> Сам PPID 1 сиротой его не делает. Критерий — отсутствие живого клиента/окна.

## Замеры этого инцидента

| Метрика | Значение |
|---|---|
| Java-таргетов возвращает `query` | **442** |
| из них провижинятся в проекты (есть `srcs` + единый source root) | **223** |
| aquery за 4-минутное окно | 130 штук, все уникальные (кеш в рамках сессии работает) |
| Чистое время aquery на эти 130 | 40.4 с (~310 мс на таргет) |
| Потолок последовательного резолва (223 проекта × 310 мс) | **~69 с** bazel на один холодный импорт |
| Итераций провалившегося импорта за ночь | ~1400 |
| Объём лога | 10 × 1 МБ за ~7 часов |
| CPU потока `Java indexing` | 141 с за 258 с жизни процесса |

> **442 против 223 — не расхождение с PERFORMANCE_PLAN.md.** `query` возвращает 442 метки,
> но `BazelQuery.parse()` отбрасывает таргеты без `srcs` и с неоднозначным source root,
> так что проектов — и, значит, вызовов `ClasspathContainerInitializer.initialize()` — ровно
> **223**. Поэтому экстраполировать 310 мс надо на 223, а не на 442: потолок
> последовательного резолва ~69 с, а не ~2.5 минуты.

## Пробелы относительно PERFORMANCE_PLAN.md

Что инцидент добавляет к уже описанному:

1. **Приёма exit 0/3 (Этап 6) недостаточно.** Она закрывает этот конкретный триггер, но при
   любом другом ненулевом коде (реальная ошибка, недоступная сеть, отозванный токен реестра)
   цикл «упал → сразу повтор» вернётся. Нужны **negative caching + экспоненциальный backoff**
   как отдельный пункт, независимо от B1.
2. **Гигиена процессов должна включать bazel-сервер.** В Этапе 6 нет пункта про то, что
   сервер переживает jdt.ls. Варианты: гасить сервер при shutdown языкового сервера, либо
   отдельный IDE-`output_base` (Этап 7) с коротким `--max_idle_secs`.
3. **Скоупинг импорта (Этап 5) помогает, но триггер сам по себе не закрывает.**
   Шаблон `//...` затягивает `rules_oci` / `helm_charts` пакеты, к Java не относящиеся вообще,
   и сузить его стоит. Но скоуп вида `//services/... + //jobs/... + //platform/...` **не**
   спас бы: падавший пакет `//platform/infra/audienzz/clamav` лежит внутри `//platform/...`.
   Триггер закрывают три вещи вместе — приём exit 3, `--nofetch` на discovery-запросе и
   переход aquery с `//...` на явный список java-меток (`--query_file` со `set(...)`).
4. **Спам в лог сам стал проблемой** — 10 МБ за 7 часов, ротация каждые 42 минуты
   затирает всю остальную историю jdt.ls. Один и тот же блок ошибок стоит логировать
   один раз, дальше — счётчиком.

## Выполненные действия

- Штатно погашен осиротевший `bazel(audienzz)` (PID 94877) через `shutdown` —
  освободилось ~1.14 ГБ. Подтверждено: процесса нет.
- Остальное **не трогалось**: jdt.ls 46531 / 49932 / 50024 имеют живых родителей
  (Code Helper (Plugin)), а `bazel(audienzz_copy)` 99557 с воркерами принадлежит открытому
  окну `audienzz_copy` — сиротами они не являются.

## Как продиагностировать в следующий раз

```bash
# 1. Кто живёт и сколько ест
ps -Ao pid,ppid,etime,pcpu,rss,command | grep -E 'jdt.ls|bazel\('

# 2. Осиротел ли jdt.ls — проверить, жив ли родитель
ps -p <PPID> -o comm=

# 3. Куда уходит CPU внутри JVM
jstack <PID> | grep -A5 'Java indexing'

# 4. Главный источник правды — лог jdt.ls нужного workspace.
#    Хеш workspace определяется по workspace.json:
grep -l audienzz ~/Library/Application\ Support/Code/User/workspaceStorage/*/workspace.json

# 5. Признак цикла повторов: много ротаций .bak_N.log и один и тот же MESSAGE
L=~/Library/Application\ Support/Code/User/workspaceStorage/<hash>/redhat.java/jdt_ws/.metadata
ls -la "$L"                       # частые ротации по 1 МБ = спам
grep -oE '!MESSAGE.*' "$L/.log" | sed -E 's/[0-9]+/N/g' | sort | uniq -c | sort -rn | head

# 6. Сопоставление output_base с workspace
cat ~/Library/Caches/bazel/_bazel_*/*/DO_NOT_BUILD_HERE
```
